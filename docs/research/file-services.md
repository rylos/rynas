# File services for rynas: research and proposal

Debian package versions come from sources.debian.org, checked on 2026-11-05.

## 0. Summary

- **The core decision:** on btrfs, **POSIX ACLs are the single source of truth for permissions**. They are the same for SMB, NFS, SFTP, FTP, the file manager (`setresuid`) and WebDAV, because the kernel enforces them. Windows ACLs via `vfs_acl_xattr` remain an advanced option, only for shares accessed exclusively over SMB.
- **In the core, phase 1:** SMB (Samba 4.22 from trixie) and NFS (kernel nfsd).
- **`file-services` plugin, phase 2:**
  - SFTP with OpenSSH;
  - rsyncd and rsync over SSH;
  - WebDAV implemented inside the file manager worker;
  - FTP/FTPS with vsftpd, LAN only.
- **Public links:** in the `files` module, through Caddy.
- **Apps:** S3 (Garage or Versity), Syncthing, DLNA, and SFTPGo for those who want it.
- **SFTPGo does not belong in the core:** it has its own permission model, which the kernel does not enforce, and an open-core license.

## 1. Samba (SMB)

### 1.1 Permission model: what others do

| System | Model | Implications for rynas |
|---|---|---|
| **DSM** | "Synology ACL": proprietary NFSv4/Windows-style ACLs, enforced by a patched kernel on btrfs/ext4 | Cannot be reproduced on Debian: no kernel patches |
| **TrueNAS** | ZFS with native NFSv4 ACLs, which map 1:1 to Windows ACLs. POSIX ACLs remain for "legacy"/multiprotocol shares. Share "Purposes" (presets): Default, Multi-Protocol, Time Machine, Final Cut Pro, Legacy | btrfs does **not** support NFSv4 ACLs. The preset idea, however, is worth taking |
| **OMV** | Share privileges rendered as `valid users`/`read list`/`write list`, plus a POSIX ACL tab on the filesystem and "Extra options" | The closest model to rynas |
| **Unraid** | Public/Secure/Private per share, Samba users | Too simplistic |

**Proposal for rynas:**

- The share × users/groups matrix (already planned in `02-ui.md`) is rendered as:
  - **POSIX ACLs** on the subvolume, both access and default, with a `share-<name>-rw`/`-ro` group or per-user entries;
  - the same lists in `smb.conf` (`valid users`, `read list`, `write list`), as a second line of defense.
- Samba options to set: `inherit acls = yes`, `map acl inherit = yes`, `store dos attributes = yes`, `nt acl support = yes`. With these, the Windows "Security" tab shows the POSIX ACLs and allows partial editing.
- **"Windows ACL" mode**, per share and advanced only: `vfs objects = acl_xattr`, which stores NT ACLs in `security.NTACL`. Suitable only for shares accessed exclusively over SMB, with a warning: NFS, SFTP and the file manager do not see these ACLs. Debian also ships `nfs4acl_xattr`, which has the same limitation.
- Why this is the professional choice: the SynoFile worker already does `setresuid` to the user. With POSIX ACLs, **every protocol sees the same permissions with no duplication**. rynas needs no permission engine of its own.

### 1.2 Configuration

**trixie packages:**

- `samba` 2:4.22.11 (4.24.7 in backports);
- `samba-vfs-modules`: contains fruit, recycle, shadow_copy2, btrfs, full_audit, catia, streams_xattr, io_uring, acl_xattr, virusfilter, worm;
- `wsdd2` 1.8.7;
- `avahi-daemon` 0.8-16.

We stay on stable. Backports will at most be an "advanced channel" option.

**`[global]` generated by rynas:**

```ini
server min protocol = SMB2_10        # no SMB1 (already the default since 4.11), no SMB2.02
disable netbios = yes                 # nmbd off; there is a "Legacy NetBIOS" toggle
server multi channel support = yes    # default on Linux since 4.15
vfs objects = catia fruit streams_xattr   # fruit must be loaded on ALL shares (AAPL is negotiated per connection)
fruit:metadata = stream
fruit:nfs_aces = no                   # prevents Macs from rewriting permissions
fruit:wipe_intentionally_left_blank_rfork = yes
fruit:delete_empty_adfiles = yes
fruit:model = MacSamba
access based share enum = yes         # hides inaccessible shares (DSM style)
interfaces = <lan>; bind interfaces only = yes
multicast dns register = no           # rynas generates the Avahi files (as OMV does)
log level = 1 auth_audit:3
```

**Per share:**

```ini
[photos]
path = /vol1/photos
vfs objects = catia fruit streams_xattr shadow_copy2 recycle btrfs
recycle:repository = #recycle         # compatible with the file manager's recycle bin
recycle:keeptree = yes
recycle:versions = yes
recycle:touch = yes
recycle:directory_mode = 0770
recycle:exclude = *.tmp,~$*,.~lock*
veto files = /@eaDir/#snapshot/.snapshots/lost+found/
hide dot files = yes
```

**Things to know:**

- **VFS module order matters:** fruit goes before streams_xattr. If a share redefines `vfs objects`, it must repeat the global ones (a classic mistake among OMV and TrueNAS users).
- **Recycle bin:** Samba never empties `#recycle`. rynas needs a task (D-TASKS), "empty after N days", like DSM's recycle bin schedule. Then two per-share options: "admins only" (`directory_mode 0700` and owned by root) or visible.
- **Previous versions:** `shadow_copy2`, as already decided. `vfs_btrfs` adds server-side copy as a clone (reflink).
- **Time Machine, "Time Machine" preset:**
  - a dedicated subvolume, with `path = /vol1/timemachine/%U` for one backup per user;
  - `fruit:time machine = yes` and `fruit:time machine max size = 1T`;
  - the Avahi service `_adisk._tcp` with `adVF=0x82`;
  - a squota limit on the subvolume (Samba's `max size` alone is not enough; OMV 8 just added "limit reported size").
  - Since 25.04.1, TrueNAS manages oplocks per share, so Time Machine and multiprotocol shares coexist on the same system. rynas must do the same: no global settings.
- **Encryption and signing:**
  - default `server smb encrypt = default` (i.e. when the client asks for it), with a per-share "Require encryption" toggle (`required`);
  - signing stays at the default: Windows 11 24H2 requires it client-side and Samba handles it;
  - AES-GCM with AES-NI is cheap even on the J4125, but a benchmark is needed before setting `required` everywhere.
- **SMB over QUIC (4.23+):** would need `quic.ko`, which is not in the Debian kernel. Phase 3 or "to watch".
- **Network discovery:**
  - **Windows:** `wsdd2`, the only package in trixie: the Python `wsdd` was **removed from testing on 2025-05-12** and has only returned in forky. It must be restricted to the LAN interface (`-i`). It also does LLMNR.
  - **macOS/Linux:** Avahi, with `/etc/avahi/services/rynas-smb.service` files publishing `_smb._tcp`, `_device-info._tcp` (model=RackMac, for the icon) and `_adisk._tcp`.
  - NetBIOS off by default.
- **Performance:** no myths (D-SYSTUNE): no `socket options` and no random buffer sizes.
  - Actually useful: multichannel (with RSS NICs or multiple NICs), `vfs_btrfs` for copies, AIO by default.
  - `io_uring` only as an experimental option.
  - `case sensitive = yes` greatly speeds up folders with more than 100k files, but breaks Windows expectations. It belongs only in a per-share "huge folders mode", with a warning: btrfs has no casefold, so there is no equivalent of TrueNAS's per-dataset casesensitivity.
- **Audit:**
  - `vfs_full_audit` with `full_audit:prefix = %u|%I|%S`;
  - logged operations: `success = connect disconnect openat renameat unlinkat mkdirat` and `failure = connect`;
  - `facility = LOCAL5`, then journald, then the rynas Log Center ("File access log", like DSM's transfer log);
  - off by default (very verbose), can be enabled per share.
- **Extra options:** per-share and global text boxes, like OMV's "Extra options" and TrueNAS's "Additional parameters" (which TrueNAS has confined to "Legacy" shares).
  - The candidate file is validated with `testparm -s` before being applied.
  - Keys managed by rynas trigger an override warning.
  - The generated file carries a header and a hash, for anti-drift.
- **Spotlight:** default `spotlight backend = noindex`, which makes the Mac search client-side. Samba's `tracker` backend is tied to Tracker 2, while trixie has tracker-miners 3.8. TrueNAS 26 introduced native per-share Spotlight ("truesearch", probably based on Elasticsearch, unconfirmed).
  - rynas, phase 3: OpenSearch/Elasticsearch app with fscrawler, then `spotlight backend = elasticsearch`.
- **AD join (phase 3, `directory` plugin):** `security = ads`, winbind, `idmap config * : backend = autorid`, and Windows ACLs start to make more sense.
- **Other ideas:** `vfs_virusfilter` with ClamAV, as an option in the antivirus plugin; `vfs_worm` for WORM folders and compliance (business).

### 1.3 Synchronized Samba passwords

- `pam_smbpass` was **removed in Samba 4.4** (2016). `tdbsam` needs the NT hash (MD4), which cannot be derived from shadow.
- **What others do:**
  - **OMV:** when the password is set from the UI it calls `smbpasswd -a -s`/`pdbedit`. If you change it with `passwd` from a shell, the Samba password does not change, and this is documented.
  - **TrueNAS:** the middleware stores the NT hash in its own DB ("SMB user" flag) and regenerates `passdb.tdb`. Since 25.x the explicit SMB flag is required.
  - **DSM:** `synouser` keeps both.
- **rynas:** every password change goes through `rynasd`, which atomically runs `chpasswd` plus `pdbedit -a -t`.
  - The NT hash (equivalent to the password) goes into SQLite **encrypted**, so `passdb` can be rebuilt, and it is exported only encrypted in `.rynasbak` (D-CFGBAK).
  - Per user: an "SMB access" toggle. Users created outside rynas get an "SMB password needs reset" badge.
  - Changing the password from a shell must be documented as unsupported.

## 2. NFS

- **Engine:** kernel nfsd (`nfs-kernel-server`, nfs-utils 1:2.8.3). Ganesha 6.5 (9.14 in backports) is for CephFS/Gluster/userspace; on a single-node NAS it only adds complexity.
- **Config:**
  - `/etc/nfs.conf.d/rynas.conf`: `vers3`, `vers4.1`, `vers4.2`, `vers4.0=n`, `threads`, and fixed ports for mountd/statd/lockd (needed for the firewall);
  - `/etc/exports.d/rynas.exports`, then `exportfs -ra`.
- **Per export:** host/subnet/IP, `rw|ro`, `sync` (default, do not change it), `root_squash` (default) / `all_squash` + `anonuid/anongid` (users picked from a menu), `no_subtree_check`, `sec=sys`.
  - Kerberos (`sec=krb5p`) in phase 3, with the directory plugin.
- **btrfs and subvolumes:** all subvolumes share the same filesystem UUID. You must **always set `fsid=<subvolume uuid>`** explicitly, otherwise handles overlap, giving "stale file handle" after a reboot or when exports are swapped. `crossmnt` only when exporting nested subvolumes.
- **UIDs and `sec=sys`:** NFSv4 passes numeric UIDs. The UI shows the UID of rynas users and warns: "clients must have the same UID".
- **Multiprotocol ("SMB+NFS" preset, as in TrueNAS):**
  - leases/oplocks disabled **only on that share** (`smb2 leases = no`, `oplocks = no`, `kernel oplocks = yes`);
  - no Windows ACL mode.
- **NFSv3 enables rpcbind (port 111):** turned on only when needed (default v4.2 only, v3 behind a toggle).

## 3. FTP / FTPS / SFTP

| | trixie version | Pros | Cons |
|---|---|---|---|
| **vsftpd** | 3.0.5 | minimal, secure, PAM, `chroot_local_user`, explicit FTPS, TLS 1.3 | upstream stalled since 2021, no SFTP |
| **ProFTPD** | 1.3.8c (1.3.9 in forky) | modules (mod_tls, mod_sftp, quotas, virtual users); used by OMV | Apache-style configuration, larger attack surface |
| **Pure-FTPd** | 1.0.50 | simple, virtual users | barely active |
| **SFTPGo** | 2.7.x (not in Debian, upstream deb) | a single service for SFTP, FTP/S, WebDAV, web client, S3/GCS/Azure backends, quotas, OIDC, LDAP via plugin, external auth hooks | AGPL-3.0 **open-core**: the Enterprise edition "gets new features first", the open-source edition gets fixes. Runs as **a single service UID**: permissions are its own, virtual, not kernel ACLs; when running as root it does `chown` after upload |
| **OpenSSH `internal-sftp`** | already installed | chroot and POSIX ACLs enforced by the kernel, keys | needs a chroot tree |

**Is FTP still needed?** Yes, almost only for **old scanners and multifunction printers**. Recent bizhub models do SMB2/3, so the UI recommends SMB and FTP appears as "compatibility".

- vsftpd with:
  - a dedicated `scanner` user, with `local_root` on the "Scans" share, write-only;
  - fixed `pasv_min_port`/`pasv_max_port`;
  - `ssl_enable` available;
  - a red warning: "Plaintext FTP: LAN only" (D-EXPOSE forbids the public profile).

**SFTP:** OpenSSH with `Match Group rynas-sftp`, `ForceCommand internal-sftp`, `ChrootDirectory /run/rynas/sftp/%u`.

- In that directory `rynasd` bind-mounts only the shares the user can access, as DSM does ("SFTP: shared folders").
- Admins keep their normal shell.

**Verdict on SFTPGo:** not as the core's single plugin.

1. It duplicates the permission model: the matrix would have to be translated into SFTPGo permissions that the kernel does not enforce, and all files would end up owned by a single UID.
2. It is not in the Debian repos.
3. It is open-core, with the risk of features moving to Enterprise.
4. rynas already provides a web client and public links through the file manager.

It fits instead as a **curated app**, for those who want virtual users, S3 backends or an FTP portal for external parties. It can be integrated with `external_auth_hook` pointed at rynas-web, which returns virtual folders matching the visible shares.

## 4. WebDAV

| Option | Notes |
|---|---|
| Apache mod_dav / nginx dav-ext | run as www-data: per-user permissions are lost |
| `caddy-webdav` (external module) | same problem, and it must be included in the `rynas-caddy` build |
| `rclone serve webdav` | one user per instance |
| SFTPGo | see above |
| **`dav-server` crate (Rust, MIT/Apache) in the `files` worker** | the worker already does per-user `setresuid`: ACLs, `#recycle` bin and quotas **identical to SMB** |

- **Proposal:** a `/dav/` endpoint inside the `files` plugin, with rynas login and app passwords (no TOTP on DAV clients).
- Exposed **only** through Caddy over HTTPS, LAN/Tailscale profile by default.
- **Clients:**
  - Windows WebClient is **deprecated** by Microsoft (2023) and has a 50 MB limit (`FileSizeLimitInBytes`): better to recommend RaiDrive or rclone;
  - macOS Finder works but is slow;
  - mobile apps and programs: Documents, Solid Explorer, FolderSync, Infuse, Joplin, Zotero, KeePass, Obsidian Remotely Save.

## 5. rsync and S3

**rsyncd** (rsync 3.4.1 from trixie, with the 2025 CVE fixes):

- `/etc/rsyncd.conf` with one module per enabled share:
  - `path`, `auth users`, `secrets file = /etc/rsyncd.secrets` (mode 600);
  - module `uid`/`gid`, `use chroot = yes`, `read only`, `hosts allow = <LAN>`;
  - `fake super = yes`, so owners and permissions from the sender (another NAS) are kept in xattrs without needing root.
- **rsync accounts separate** from rynas users, like DSM's "rsync accounts": the daemon password sits in plaintext in the secrets file.
- **Hyper Backup compatibility**, "rsync-compatible server" destination: daemon mode, account and module with write access. There are two modes: "single-version copy" (readable files) or multi-version (`.hbk` format, readable only with Synology tools). The UI must say so.
- **rsync over SSH:** keys in `authorized_keys` with `command="rrsync -wo /vol1/backup/x",restrict` (`rrsync` already ships in the rsync package). This is the recommended way beyond the LAN: the daemon protocol is not encrypted.

**S3 as a backup destination (app, not core):**

| Product | Status 2025-2026 | Assessment |
|---|---|---|
| **MinIO** | community edition in maintenance since 2025-12-03, "no longer maintained" on 2026-02-12, **repo archived on 2026-04-25**; no binaries since October 2025 and console removed in May 2025 | **avoid** (the pgsty/minio fork exists) |
| **Garage** | v2.x (AGPL, Rust), lightweight, designed for self-hosting | excellent for a single node; lacks object lock, so no immutable backups |
| **Versity S3 Gateway** | Apache-2.0, POSIX backend: objects are regular files | turns an existing btrfs share into S3, with rynas snapshots and quotas; versioning and object lock on POSIX still to be verified |
| **SeaweedFS** | Apache-2.0, feature-rich | heavier, suited to clusters |
| **RustFS** | Apache-2.0, MinIO-compatible | young, not yet production-ready |

For restic and kopia there is also `rest-server --append-only` (already in the backup plan).

## 6. Other protocols

- **AFP:** no. Apple is removing it and Time Machine goes over SMB.
- **iSCSI, phase 3:** `targetcli-fb` 2.1.53 (LIO). File-backed LUNs in a `nodatacow` subvolume (`chattr +C`), with a warning about snapshots.
- **DLNA:** `minidlna` 1.3.3, upstream nearly stalled. Ships as an app; those who want more use Jellyfin with the DLNA plugin.
- **Syncthing:** app (trixie 1.29.5; upstream is at v2 with a SQLite DB), with the shares mounted and the same `PUID`.
- **Public links, in the `files` module, phase 2:**
  - random 128-bit token, expiry, password (argon2), download limit;
  - write-only "file request", like DSM's File Request;
  - Caddy route `share.<domain>/s/<token>` **without** forward_auth, with rate limiting and audit;
  - requires the public profile with explicit confirmation (D-EXPOSE); otherwise links work only on LAN/Tailscale.

## 8. Mistakes to avoid

- Mixing Windows ACLs (xattr) and POSIX ACLs on the same share, or building a permission engine into rynas.
- Redefining `vfs objects` per share and losing `fruit` or the correct order: Time Machine and Mac metadata break.
- A `shadow:format` that differs from btrbk's naming: the previous versions tab stays empty.
- A recycle bin without cleanup: disks fill up without anyone noticing.
- NFS exports of subvolumes without `fsid`.
- Samba passwords that are out of sync with no indication in the UI.
- SMB, NFS, rsyncd or FTP exposed to the Internet: forbidden, they are reachable only via VPN or Tailscale.
- MinIO community edition.
- Relying on the Windows WebClient.
- Following the Python `wsdd` from old OMV documentation instead of trixie's `wsdd2`.
- Removing the `testparm`/`exportfs` check before apply.
