# Analyst report: Task Scheduler and LXC/VM for rynas

**Summary.**
- **Topic 1**: a single rynas Task Scheduler, built on **persistent systemd units generated by `rynasd`** (`/etc/systemd/system/rynas-task-<id>.{service,timer}`). Result and output are read from the journal via `INVOCATION_ID`, plus an `ExecStopPost` hook. Existing cron jobs are shown read-only.
- **Topic 2**: **do not write an LXC/VM manager**. Integrate **Incus** (in Debian 13: 6.0.4 LTS in main, 7.0.2 LTS in trixie-backports) with a thin `instances` plugin, as done for docker. btrfs storage on a subvolume of the NAS volume, bridge taken from the network module.

## Topic 1: scheduled tasks

### 1.1 Comparison

| Product | Engine | Triggers | User | Output/notifications | Run now / history | Notes |
|---|---|---|---|---|---|---|
| **Synology DSM** Task Scheduler | own (cron-like) | scheduled + **triggered** (boot/shutdown) | root or user | **mail with output (max 1 MB)**, "only on abnormal termination" option | Run; "View results" | UX reference model |
| **TrueNAS** | cron (Cron Jobs) + Init/Shutdown Scripts | cron; PREINIT/POSTINIT/SHUTDOWN with timeout | chosen user | mail of stdout/stderr, can be suppressed | "Run now" | two separate screens (not unified) |
| **OMV** Scheduled Jobs | cron, `/etc/cron.d/openmediavault-userdefined` | cron, @reboot | chosen user | mail to the user (or catch-all) via Postfix | Run | simple and transparent |
| **Unraid** User Scripts | cron + `at` | presets/custom, array start/stop | root | log in `/tmp/user.scripts/.../log.txt` (grows without limit) | Run / Run in background | much loved for its simplicity. Recurring bugs: custom cron entries that never fire, "abort" that does not stop the script |
| **Cockpit** | systemd | timers (Timers tab, "Create timer") | — | journal | start/stop service | transparent, little guidance |
| **Webmin** | cron | cron, @reboot | any | cron mail | Run now | generic |
| **Proxmox VE/PBS** | own scheduler (`pvescheduler`) with **systemd calendar-event syntax** | scheduled | — | UPID task log, notifications | Run now, task history | systemd syntax even without systemd |

### 1.2 cron or systemd timers

| | cron/anacron | **systemd timer** |
|---|---|---|
| Catching up missed runs | anacron, daily granularity only | `Persistent=true` on any timer |
| Jitter | no | `RandomizedDelaySec=`, `FixedRandomDelay=` |
| Overlapping runs | yes (needs `flock`) | **no**: if the service is already active the timer does not start another |
| Output | cron mail (MTA) | **journal**, filterable per unit and per run (`_SYSTEMD_INVOCATION_ID`) |
| Result | nothing structured | `Result`, `ExecMainStatus`; in `ExecStopPost` the variables `$SERVICE_RESULT`, `$EXIT_CODE`, `$EXIT_STATUS` |
| Timeout | no | `RuntimeMaxSec=` |
| Resources | `nice` | cgroup: `CPUWeight`, `IOWeight`, `MemoryMax`, `Nice` |
| Security | none | `User=`, `ProtectSystem=`, `NoNewPrivileges=`, `PrivateTmp=`… |
| Run now | launch by hand | `systemctl start rynas-task-X.service` (same environment as the scheduled run) |
| Event triggers | no | `.path` (files), udev, target dependencies |
| Preview | no | `systemd-analyze calendar --iterations=5 '<expr>'` |

Debian 13 (systemd 257) also has `OnSuccess=` and `OnFailure=`. The `cron` package may not even be installed: with systemd, rynas does not depend on it.

### 1.3 Best ideas, with source
- **Mail with output and an "only on error" option, 1 MB limit** (DSM).
- **Boot and shutdown triggers on the same screen as schedules** (DSM; TrueNAS keeps them on two screens, which is worse).
- **Script pasted into the UI**, without having to create a file by hand (Unraid, DSM).
- **systemd calendar-event syntax** for internal tasks too (Proxmox/PBS).
- **Generated files visible on disk** (OMV uses `/etc/cron.d`; for rynas: units in `/etc/systemd/system` with a "managed by rynas" header).
- **View of system timers** (Cockpit): `apt-daily`, `fstrim`, `e2scrub_all`, `logrotate`, read-only.

### 1.4 Mistakes to avoid
- **Script run as root but editable by a user**: the classic DSM problem with scripts stored on a share. It opens a privilege escalation.
- **Unbounded logs** (Unraid, 179 MB): rotation and a per-run cap are needed.
- **"Abort" that does not stop the process** (Unraid): with systemd, `systemctl stop` kills the whole cgroup.
- **Custom cron entries that never get written** (Unraid): the expression must be validated and shown with its next runs.
- **Mail that only arrives with a local MTA configured** (OMV, cron): rynas uses its own notification channel (mail, ntfy, Telegram, already in phase 1).

### 1.5 Recommendation: a single rynas "Task Scheduler"

**Task types in the same list:**
1. **Internal** (snapshots, scrub, SMART tests, backups, apt update checks, Incus snapshots): locked command, editable schedule and notifications. `ExecStart=/usr/lib/rynas/rynasctl job run <id>`, which asks `rynasd` to create the UPID task, so they also show up in the task panel.
2. **User**: command or script (with editor), user, schedule, trigger, timeout, resources, notifications.
3. **External, read-only**: non-rynas system timers, `/etc/crontab`, `/etc/cron.d/*`, `/var/spool/cron/crontabs/*`. Computed next run and a "Convert to rynas task" button, which comments out the original line after confirmation.

**Generated units** (example):
```ini
# /etc/systemd/system/rynas-task-42.service
# Managed by rynas — do not edit (sha256:…)
[Unit]
Description=rynas task 42: rsync photos
RequiresMountsFor=/volume1
[Service]
Type=oneshot
User=admin
ExecStart=/var/lib/rynas/tasks/42/run
ExecStopPost=/usr/lib/rynas/rynasctl task-finished 42
RuntimeMaxSec=2h
Nice=10
IOWeight=50
NoNewPrivileges=yes
PrivateTmp=yes
# /etc/systemd/system/rynas-task-42.timer
[Timer]
OnCalendar=Mon..Fri 02:30
Persistent=true
RandomizedDelaySec=5m
AccuracySec=1s
[Install]
WantedBy=timers.target
```

**Triggers:**
- **Boot**: no `.timer`. The unit has `WantedBy=multi-user.target`, `After=network-online.target rynasd.service`, `RequiresMountsFor=`. Alternatively `OnBootSec=`.
- **Shutdown**: `Type=oneshot`, `RemainAfterExit=yes`, `ExecStart=/bin/true`, `ExecStop=<script>`, `TimeoutStopSec=`. Ordering `After=` on mounts and network ensures the script runs *before* those are stopped.
- **Event**: `.path` units (file or folder changed). rynas events (USB disk plugged in, pool degraded, UPS on battery) via a `rynasd` hook that calls `StartUnit`.

**Execution and history:**
- `rynasd` uses zbus on `org.freedesktop.systemd1` (already planned in the architecture): `StartUnit`, `StopUnit`, the timer's `NextElapseUSecRealtime` and `LastTriggerUSec` properties, the service's `Result` and `ExecMainStatus`.
- The `task-finished` hook receives `$SERVICE_RESULT`, `$EXIT_CODE`, `$EXIT_STATUS` and `$INVOCATION_ID`. It writes a row to SQLite (id, invocation, start, end, result, code) and decides on notification: always, only on error, or never.
- **Output**: read with `journalctl -o json _SYSTEMD_INVOCATION_ID=<id>`, or with sd-journal (`systemd`/libsystemd crate, streaming reads for the live log WebSocket). The last ~256 KB are copied into SQLite, because the journal rotates and history must not be lost. Mail attaches at most 1 MB (like DSM).
- **Visual editor**: presets (hourly / daily / weekly / monthly / every N minutes), an `OnCalendar` expression field and a preview of the next 5 runs via `systemd-analyze calendar`. Also accept **cron syntax** and convert it, because users know it.
- Do not use `proxmox-time` (AGPL, incompatible with BSL): validate with `systemd-analyze`.
- **Transient runs** (`systemd-run --unit=rynas-adhoc-…`) only for "run a command once" from the terminal or task panel, not for saved tasks.

**Security:**
- `User=root` only for the admin role; choosing other users is admin-only; a non-admin user can create tasks only as themselves (phase 2).
- Scripts live in `/var/lib/rynas/tasks/<id>/run`, `root:root 0700` (or owner = the task's user).
- If a task points to an external file with `User=root`, `rynasd` **rejects** the path when the file or any parent directory is writable by non-root.
- Audit (who created, edited or ran it, script diff); unit hashes with anti-drift (D-CFG); `systemctl daemon-reload` inside the transactional apply.
- Secret variables (rclone tokens etc.) passed via `LoadCredential=` instead of in plain text in the script.

**Landed (2026-11-14, issue #12): live output of a running task.** The output of the current
invocation is streamed from the journal (`_SYSTEMD_INVOCATION_ID=`) as server-sent events while
the unit runs, timer runs included, and becomes the normal history entry when it ends. Design,
events, caps and the journald `\r` limitation are in `docs/phase1/plan.md` ("Live output" under
the Task Scheduler API).

### 1.7 Phases
- **Phase 1**: systemd engine, internal tasks (snapshots, scrub, SMART) and user tasks with calendar and boot triggers, run now, history, notifications, admin only, read-only view of cron and system timers.
- **Phase 2**: shutdown and event triggers, resource limits and sandboxing from the UI, cron conversion, tasks for non-admin users, `LoadCredential`.
- **Phase 3**: dependencies between tasks (chains), multi-NAS (business), script templates (backup, cleanup).

## Topic 2: LXC and VMs

### 2.1 Comparison

| | Technology | Status 2025-2026 | Strengths | Limits |
|---|---|---|---|---|
| **Proxmox VE 9.x** | LXC (pct) + QEMU/KVM | 9.1 (Nov 2025): **OCI images → LXC**, "application containers" in tech preview | templates, snapshots, backups, best UX | a full hypervisor, not something to embed |
| **Incus** | LXC + QEMU, REST API, daemon | Debian 13: **6.0.4 LTS** (main, Debian security updates, upstream until June 2029); **7.0.2 LTS** in trixie-backports (until June 2031; requires kernel 6.12, fine for trixie; adds OCI application containers) | mature API, images, profiles, btrfs driver, scheduled snapshots, VMs and containers through one API, Apache-2.0 | `incus-ui-canonical` **is not in Debian** (Zabbly repo only) |
| **LXD** | same as Incus | Canonical, distributed as a snap, AGPLv3 + CLA since December 2023 | — | snap on Debian, license and governance less suitable |
| **TrueNAS** | 25.04: VMs and LXC on Incus → **25.04.2/25.10: VMs back on libvirt**, LXC experimental → **26 (beta, June 2026): LXC "fully supported"**, HA, GPU passthrough | LXC backend in 26 not stated in the docs (forums suggest it is still Incus) | migration path from CORE jails | VM migration broken between releases: strong complaints |
| **Unraid** | built-in libvirt VMs; LXC via community plugin | — | simple VMs with passthrough | LXC unofficial |
| **Synology VMM** | proprietary QEMU | — | excellent UX (virtual switches, snapshots, HA) | closed |
| **Cockpit-machines** | libvirt | — | simple | VMs only, no LXC |
| **libvirt/virt-manager** | QEMU (+ libvirt-lxc) | libvirt-lxc rarely used | standard for VMs | weak LXC, no images |
| **systemd-nspawn** | machinectl/importctl | — | already on the system | no image ecosystem or UX |

### 2.2 Best ideas
- **Delegate to a mature API** (TrueNAS with Incus for LXC; Proxmox has its own stack). For rynas this means Incus via the `/var/lib/incus/unix.socket` socket.
- **Ready-made templates and images** (Proxmox, `images.linuxcontainers.org` in Incus).
- **Bind mounts of shares into the container with idmap** (Incus `disk` device with `shift=true`): the main NAS use case ("Plex/Jellyfin in LXC that sees /volume1/media").
- **Native scheduled snapshots** (Incus `snapshots.schedule`, `snapshots.expiry`) shown in the Task Scheduler as read-only internal tasks: this ties the two topics together.
- **Virtual switch / LAN bridge** (VMM): `br0` bridge from the network module with test and rollback.

### 2.3 Mistakes to avoid
- **Switching backend between releases** (TrueNAS 25.04 → 25.10): VMs no longer started and a migration tool was missing. Pick once and keep a standard format (exportable qcow2/raw, `incus export`).
- **Docker inside unprivileged LXC** as a promoted use case: problems with fuse and AppArmor even in TrueNAS 26 beta. Docker already has its own plugin.
- **Proprietary state** in rynas: Incus remains the source of truth. rynas does not duplicate instance configuration.
- **macvlan as the default**: the host cannot talk to the guest. A bridge is better.
- **Promising heavy VMs on 4 GB**.

### 2.4 Recommendation

**A thin `instances` plugin (containers + VMs) on top of Incus**, phase 3 as per the roadmap, along the same lines as D-DOCKER:
- **Package**: Debian trixie's `incus` (6.0 LTS, Debian security updates). Advanced option: 7.0 from trixie-backports. VMs need `qemu-system-x86` and `ovmf`, pulled in via `incus`'s recommends.
- **Access**: only `rynasd` talks to the Incus socket. The `incus-admin` group is equivalent to root, so it must not be given to the `rynas` user. rynas ACLs on top.
- **Storage**: Incus `btrfs` pool with `source=/volume1/@incus`, a dedicated subvolume. Native btrfs snapshots and quotas, visible in the storage module.
- **Network**: default `incusbr0` (NAT) to start with; an "on the LAN" option with the `br0` managed by rynas network.

**The plugin DOES:**
- install and adopt Incus (`incus admin init` preseed), list instances;
- "create from image" wizard (Debian, Ubuntu, Alpine…);
- start, stop, restart, autostart;
- CPU and RAM limits;
- share mounts (idmap);
- text console (Incus `exec`/`console` WS proxied over rynas WS);
- manual and scheduled snapshots, export/import.

**The plugin DOES NOT:**
- clustering;
- its own app catalog;
- OCI containers (those stay in the docker plugin);
- OVN networks;
- live migration;
- graphical VM console before phase 3b (VGA/SPICE via `incus console --type=vga`, later);
- GPU/PCI passthrough from the UI ("advanced" only);
- a full UI: optional link to `incus-ui-canonical` if the user adds the Zabbly repo.

**VMs**: also through Incus (one API). rynas has no pre-existing libvirt VMs to preserve, which was the reason TrueNAS went back to libvirt. libvirt remains only an option to evaluate if specific requests emerge (importing existing XML).

### 2.5 Hardware
- **DS923+ (Ryzen R1600, 2C/4T, AMD-V, 4-32 GB)**: LXC without problems even with 4 GB. Light Linux VMs with 8 GB or more. Windows realistic only with 16 GB or more.
- **DS920+ (Celeron J4125, 4C, VT-x, 4-8 GB max)**: LXC yes; at most one small Linux VM.
- **Warnings**: the UI checks `/dev/kvm` and free RAM and warns before creating a VM.

### 2.6 Phases
- **Phase 2**: no plugin. Groundwork only: the `br0` bridge in the network module and the `@incus` subvolume planned in the volume layout.
- **Phase 3a**: `instances` plugin, LXC only (installation, wizard, shares, snapshots, text console, linked Task Scheduler).
- **Phase 3b**: Incus VMs (ISO, cloud-init, VGA console, limits), backups through the `backup` plugin (`incus export` or btrfs send).
- **Phase 3c / business**: Incus 7 OCI containers (evaluate overlap with docker), guided passthrough, replication between NASes.
