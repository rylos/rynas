## Verified and fine

- **REST path safety** (`repo.rs:55-80`): the type is one of five fixed names, object names must
  be 64 lower-case hex characters, the group's folder comes from the registry (never from the
  URL), `serve_file` opens with `O_NOFOLLOW`. No traversal found.
- **Append-only**: `config` and `keys` refuse POST, DELETE only for `locks`, uploads are hashed
  while streaming and the name must equal the SHA-256 (`repo.rs:406`); placement is `link(2)`,
  which cannot replace an existing name (`repo.rs:412`). Restore sessions only read
  (`repo.rs:159-171`). A device token reaches only its own group (`repo.rs:99-104`).
- **Uploads stream**: a bounded channel (16 chunks) to a blocking writer, nothing held whole in
  memory; the size and quota limits are enforced while the body arrives (`repo.rs:368-385`).
  rynas-web streams both ways with `Limited` (`rynas-web/src/pc_agent.rs:88`) and passes only
  five request headers.
- **423**: the write slot and the maintenance gate are taken under one lock (`repo.rs:324-338`,
  `maint.rs:571-588`); the agent waits out 423 for up to an hour (`rynas-agent/src/backend.rs:136`).
- **Prune never deletes at once**: `PruneOptions::default()` keeps `instant_delete = false` and
  `keep_delete = 23h` (rustic_core 0.13.0 `prune.rs:141-143`), so packs uploaded by a backup that
  is still running when a maintenance starts are only marked, and recovered when indexed. This
  is the real guard (rustic ignores locks); the ten-minute quiet gate only narrows the window.
- **Codes and tokens**: 60-bit codes from `getrandom` with no modulo bias (`mod.rs:100-111`, 256
  is a multiple of 32), 256-bit tokens, only SHA-256 stored, codes removed before use (single
  use, `mod.rs:1389-1395`, `1495-1501`), 15 min / 1 h expiry.
- **Agent**: the pin is checked on the end-entity certificate and the handshake signature is
  still verified (`http.rs:55-96`); every command runs from an argv vector without a shell
  (`restore/exec.rs:38-80`); state is `0600` in a `0700` folder, written with `O_NOFOLLOW` +
  fsync + rename (`state.rs:61-85`); freezes are undone by drop, watchdog, signal handler and
  the next start, and nothing is written to a frozen filesystem (cache off, state later).
- **Restore wipe safety**: the target is checked twice (choice and just before `wipefs`,
  `exec.rs:205`): mounted partitions by `maj:min` in mountinfo, swap, holders; the TUI makes the
  user type the disk's name, the scripted mode needs `--confirm <disk>` and `--fingerprint`.
- **btrbk retention** (`pc_backup.rs` `retention_plan`, `prune`): the newest complete snapshot of
  each subvolume is always kept (`receive::parents`), future-dated names are never deleted,
  the NAS floor applies, interrupted receives are kept while a receive runs or for an hour; the
  pass takes the same `flock` as the receive filter (non-blocking, skips when a receive runs),
  re-scans under the lock and deletes only subvolumes directly inside the locked descriptor
  (`destroy_subvolume(dir, name)`), at most 50 per pass. No data-loss path found.
- **Processes**: actions re-identify the process by start time before acting
  (`processes.rs:615-625`); PID 1, kernel threads, rynasd, protected units and the SSH listener
  are refused; the sampler is on demand, reuses per-process metadata across samples and drops
  its state when idle (`trim_idle`). Its cost is a few `/proc` reads per process: acceptable on
  a 2-core NAS.
- **Zip**: stored entries, zip64, data descriptors; the worker writes through a 1 MiB
  `BufWriter`, rynasd forwards 256 KiB chunks; nothing whole in memory.
- **Docker log reconnect** (`containers.rs:291-309`): every access in the timer is `try_`, the
  stream is cleared before reopening, so no repeated tail.
- **API**: console routes behind `admin_only`, an audit line on every change, routes in plan.md
  and proxied; agent routes need no CSRF by design and carry no session.
- No product comparisons in the new UI texts; `restic`/`btrbk` appear only as the tools the user
  runs. No inline styles; one new CSS rule with tokens.

## High

**H1. A restore session dies one hour after login, so any bare-metal restore longer than that
fails half-way and leaves an erased disk.**
`restore_login` sets `expires_ms = now + SESSION_TTL_MS` (1 h, `pc_agent/mod.rs:58`, `1504`), and
`session_devices` drops expired sessions on every check (`mod.rs:570-576`). Nothing extends it.
The agent reads the whole repository with that token (`restore/restic.rs:38`), and its backend
treats 401 as final (`rynas-agent/src/backend.rs:65`). At 100 MB/s an hour is about 350 GB, less
on Wi-Fi or a busy NAS, and the time the user spends in the TUI counts too. By then the disk is
wiped and partly restored. The closing `restore/report` fails as well, so the NAS never
records why. Sessions are also kept only in memory (`mod.rs:282`), so restarting rynasd (an
update, a crash) cuts off every restore that is running.
*Fix:* a sliding expiry: each accepted request pushes `expires_ms` to now + 1 h, with an
absolute cap (for example 48 h). Keep the session hashes in the registry, so they survive a
restart. Let the agent's backend retry a 401 once by logging in again only when it still holds a
valid code (or skip that and rely on the sliding expiry). Add a test that keeps a session alive
past the TTL with requests.

## Medium

**M1. Every uploaded file rewrites and fsyncs the whole registry on the async runtime, while
holding the lock every REST request needs.**
After each placed object, `add_used` (`maint.rs:136-152`, called at `repo.rs:438`, inside the
async `upload`) runs `svc.edit`. That clones the registry, pretty-prints it (history included),
and `write_atomic`s it with fsync under `reg`'s mutex (`mod.rs:349-364`). A first backup of
500 GB means tens of thousands of fsyncs. Each one blocks a tokio worker thread (two on a
2-core NAS), and `device_of_token` (`mod.rs:548`) waits on the same mutex for every repository
request. `used_bytes` likewise walks the whole repository with `dir_size` on the async thread
the first time after a restart (`repo.rs:322`, `maint.rs:113-127`).
*Fix:* count `uploaded_bytes` in `Live` (memory) and persist it with the run's report or at most
once a minute. Move the first `dir_size` to `spawn_blocking` at start-up (or in
`count_used`), so the upload path never walks the disk.

**M2. Ten wrong codes from anyone lock pairing and restore for everybody.**
`check_rate`/`failed` (`mod.rs:406-432`) keep one global counter, and the agent routes need no
session. Any client that reaches the web port can send one wrong code a minute and keep every
pairing and every restore code refused, which hurts most during a disaster recovery. rynas-web
already passes the client address (`rynas-web/src/pc_agent.rs:81-86`).
*Fix:* count failures per client address (10 in 10 min per address), plus a much higher global
cap (for example 200) as a second fence. With 60-bit codes, even the global cap leaves brute
force hopeless.

**M3. A restore code hands out the group's NAS key password, which outlives the session.**
`restore_login` answers `repo_password: svc.nas_password(&g)` (`mod.rs:1522`). That is the key
the NAS uses for maintenance, valid for every PC of the group, and it never changes. Anyone who
saw one restore screen, log or script (`--code` scripted runs) can decrypt any copy of the group
folder from then on. The REST layer stays read-only, but the secret does not expire with the
session.
*Fix:* at login, add a temporary key (`WorkerOp::AddKey`, host `restore-<device>`). Return its
password, and remove the key when the session ends or expires (on the report, or from the watch
loop). Say in the console that a restore code gives read access to the whole group when the
group is shared.

**M4. The pairing command does not carry the fingerprint, and `--yes` skips the check.**
The console's command is `sudo rynas-agent pair {url} CODE` (`mod.rs:919`), although
`PairingCreated.fingerprint` is known. In `pair` (`rynas-agent/src/main.rs:124-133`), no
`--fingerprint` plus `--yes` accepts whatever certificate answered. That is trust on first use,
and anyone in the path can take the pairing code and the PC's repository password, or pose as
the NAS for every later backup.
*Fix:* put `--fingerprint <fp>` in the generated command when TLS has a fingerprint. Make
`--yes` refuse to go on without `--fingerprint` over https, the same as the scripted restore
does (`restore/mod.rs:120`).

**M5. The quota check races between concurrent uploads.**
`used` is read before the lock (`repo.rs:322`), and the check at `repo.rs:330` counts neither
the bytes other uploads in flight have declared nor the ones they are still writing. The
streaming limit (`repo.rs:341`) uses the same stale `used`. restic uploads several packs at once,
so a group can overshoot its quota by about the number of parallel uploads × the pack size, up
to 1 GiB each.
*Fix:* keep a `reserved` counter in `Live`. Under the lock, check `used + reserved + declared ≤
quota` and add `declared` (or a pack-size estimate when there is no Content-Length). Subtract
it when the `Writing` guard drops, and compute `limit` from that.

**M6. A download that fails half-way ends as a clean, truncated file.**
`stream` (`maint.rs:852-927`) returns 200 after the first 64 KiB, and the `unfold` ends the body
on stdout EOF (`Ok(0) => None`) without looking at the worker's exit status or its `Error`
event. If the worker fails mid-file (a missing pack, a read error, OOM), the browser saves a
shorter file and reports success. A zip at least lacks its central directory; a single file
has nothing to show it.
*Fix:* at EOF, `child.wait()` and read the last stderr event. If the exit status is not zero,
yield an `Err`, so hyper aborts the chunked body and the browser marks the download failed.
For single files, have the worker write the size first (or answer `Content-Length` from a
`stat` read), so a short body is detectable.

**M7. Reads and downloads load the whole index outside the memory budget, also during a
maintenance.**
`Stream` and the browse and versions reads open the repository `to_indexed()`
(`rynas-backup-worker/src/main.rs:802`). That costs the same order of memory as the prune
estimate (~200 B per blob). They run with `READ_TIMEOUT` only and no `MemoryMax`
(`maint.rs:154-173`, `mod.rs` `read_op`), two streams plus reads at once, and nothing stops them
while a maintenance holds its own budget. On a 2 GB NAS with a few million blobs, a
maintenance plus two downloads can exceed the RAM, and the OOM killer may pick rynasd or the
maintenance.
*Fix:* start reads through the unit launch with `MemoryMax` too. While a maintenance runs in
the group, refuse downloads and zips with 423/409, or cap them at `budget - estimate`. Show the
estimate in the download error.

## Low

**L1. A second upload of an existing name is accepted after only a size check**
(`repo.rs:422-430`). If the stored object was damaged (bit rot, a partial copy), the PC is told
"already there" and never re-sends it. *Fix:* when the sizes match, hash the existing file
(rarely needed: only on a name collision). If it differs, put the verified temp file in its
place with `renameat2(RENAME_EXCHANGE)` and keep the old one aside for the check to report. The
content is proven by its hash, so append-only holds.

**L2. Upload temp files are never swept.** `.tmp-<pid>-<rand>` (`repo.rs:343`) is removed only
when the handler runs to the end. If rynasd crashes or restarts mid-upload, the file stays
forever and counts in `dir_size`. *Fix:* have the maintenance (or the start-up count) delete
`.tmp-*` files older than a day in `data/??/` and the type folders.

**L3. A pairing race can overwrite a device.** `pair` picks the device name from a snapshot
taken before two worker calls (`maint.rs:261-262`), then `r.devices.insert` (`maint.rs:352`)
replaces any device that took the same name meanwhile: two PCs with the same host name paired
at the same moment. The first PC's token stops and its key file is orphaned. *Fix:* inside the
final `edit`, re-run `unique` against the live registry (or reserve the name in `Live` first).

**L4. Deleting a group can overlap a maintenance or a pairing.** `delete_group` checks
`maintaining` without setting anything (`maint.rs:397-402`). A pairing that joins the group
(`PairingRequest.group`) is still valid while the group is deleted, and its new device is
then removed with the group (`maint.rs:411-416`). *Fix:* take the group with `take()` for the
deletion, and delete the pending pairings that name the group, both under the registry lock.

**L5. The wipe check misses claims that are not in mountinfo or `holders`**
(`restore/exec.rs:105-132`): a member partition of a multi-device btrfs mounted from another
disk, a ZFS vdev, a second `rynas-agent restore` on the same disk. *Fix:* open the disk with
`O_EXCL` before `wipefs` (Linux refuses an exclusive open of a block device that is mounted, in
a mapping, a btrfs member, or opened `O_EXCL` by another process), keep that descriptor for the
GPT write, and report "in use" when it fails.

**L6. Processes: a small window between the check and `kill(2)`** (`processes.rs:724-737`):
the PID can end and be reused between `identify` and `kill`. *Fix:* `pidfd_open`, then
re-identify (start time from `/proc/<pid>/stat`) and send with `pidfd_send_signal`. The same
applies to `setpriority`/`ioprio_set`. (Code already on `origin/main`.)

**L7. A successful run shows "Up to date".** The drawer's history status uses
`t("upd.uptodate")` for an ok run (`pages/backup/agent.rs:617`), the Updates page's word.
*Fix:* a key of its own (`pca.h.ok`: "Completed" / "Completato").

**L8. The zip of a selection travels in the query string** (`agent.rs:880`, `mod.rs:1219-1239`,
up to 1000 paths of up to 4096 bytes each). Large selections exceed the URL and header limits of
hyper and browsers (414/431) and show a raw error. *Fix:* a POST with the paths in a form body
(still a download via a hidden form), or cap the selection's total length in the UI with a
message.

**L9. `rynas-agent` is its own workspace but is missing from the root `exclude`**
(`Cargo.toml:4`; it works because the crate declares `[workspace]`). Neither it nor
`rynas-backup-worker` is covered by `cargo test --workspace`/clippy. *Fix:* add it to
`exclude` for clarity, and list both crates' test and clippy commands in the review playbook /
`docs/quality/guidelines.md` §verification.
